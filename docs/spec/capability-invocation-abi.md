# Capability Invocation ABI

## Purpose

This document freezes the boundary between any planning/reasoning
runtime and the Crabedence execution kernel.

The ABI is intentionally minimal. The planner sends what it wants
done and who authorized it. Crabedence independently determines
how it is executed, what authority policy applies, and which
provider handles it.

## The ABI

A capability invocation is a single JSON object:

```json
{
  "capability": "gmail.message.send",
  "arguments": {
    "to": "bob@example.com",
    "body": "Hello"
  },
  "principal": "user@example.com",
  "grant_id": "mail-send-grant",
  "idempotency_key": "send-001"
}
```

### Required fields

| Field            | Type   | Description                                      |
|------------------|--------|--------------------------------------------------|
| `capability`     | string | Registered capability identifier                 |
| `arguments`      | object | Arguments for the capability (validated by schema) |
| `principal`      | string | Identity of the requesting principal             |

### Conditionally required fields

| Field              | Type   | Required when                          |
|--------------------|--------|----------------------------------------|
| `grant_id`         | string | Capability's authority policy requires a grant |
| `idempotency_key`  | string | Execution class is MUTATION or CRITICAL |

### Optional fields

| Field              | Type   | Description                                      |
|--------------------|--------|--------------------------------------------------|
| `execution_class`  | string | Caller assertion; checked against registry. If absent, registry's pinned class is used. Mismatch = DENIED. |
| `deadline`         | string | RFC3339 timestamp; request is DENIED after this time |

### Fields the planner must NOT send

These are security-relevant properties pinned below the planner,
inside Crabedence's registry:

- `authority_policy` — resolved from the capability descriptor
- `provider` / `adapter` — resolved from the capability descriptor
- `schema` — resolved from the capability descriptor
- `receipt_version` — determined by Crabedence
- `evidence` — generated by Crabedence

If a planner sends these, they are ignored. Crabedence does not
trust caller-supplied values for security-relevant properties.

## Transport

The ABI is transported over a Unix-domain socket with length-prefixed
framing:

```
[4-byte big-endian length] [UTF-8 JSON body]
```

Maximum message size: 4 MiB.

This transport is stable. Any planner that can open a Unix socket
and write JSON can invoke capabilities.

## What Crabedence resolves independently

When a request arrives, Crabedence:

1. Looks up the capability in its registry.
2. Resolves the execution class (PURE, READ, MUTATION, CRITICAL).
3. Resolves the argument schema and validates arguments.
4. Resolves the authority policy and verifies the grant.
5. Resolves the adapter/provider binding.
6. Checks idempotency requirements.
7. Admits or denies.
8. Dispatches to the provider.
9. Generates evidence and receipts (for CRITICAL).
10. Returns a typed outcome.

The planner has no influence over steps 2-9. It can only assert
the execution class (step 2), which is checked against the registry.

## Execution path differentiation

Crabedence supports different execution paths based on the
registry-pinned execution class:

| Class     | Path                  | Durable | Evidence | Idempotency |
|-----------|-----------------------|---------|----------|-------------|
| PURE      | Local runtime         | No      | No       | No          |
| READ      | Lightweight admitted  | No      | No       | No          |
| MUTATION  | Durable execution     | Yes     | No       | Yes         |
| CRITICAL  | Durable + evidence    | Yes     | Yes (V3) | Yes         |

PURE capabilities execute in the calling process — no socket hop.
READ capabilities go through admission and authority but skip
durable idempotency.
MUTATION capabilities require durable idempotency (PostgreSQL).
CRITICAL capabilities require durable idempotency plus V3
evidence and receipt signing.

## Response

```json
{
  "status": "SUCCEEDED | FAILED | DENIED | UNKNOWN",
  "result": {},
  "error": "human-readable error",
  "failure_code": "UNAUTHORIZED | ...",
  "evidence": {
    "digest": "64-char hex SHA-256",
    "receipt_version": 3
  },
  "execution": {
    "provider": "gmail-adapter",
    "run_id": "run-..."
  }
}
```

`IN_FLIGHT` is a valid wire status but is converted to `UNKNOWN`
at the NEMO boundary — it is not a terminal outcome for the caller.

## Stability guarantee

This ABI is frozen. Changes are additive only:
- New optional request fields may be added.
- New response fields may be added.
- Existing fields will not be removed or change semantics.
- The transport (Unix socket, length-prefixed JSON) will not change.

Any planner — Hermes, OpenAI Agents SDK, LangGraph, custom —
can target this ABI and remain compatible with future Crabedence
versions.
